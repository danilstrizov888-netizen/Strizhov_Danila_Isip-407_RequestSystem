Архитектура системы учёта заявок

\---

&#x20;  1. Выбранная архитектура



Слоистая архитектура: presentation → service → repository → database.



\---



&#x20;  2. Слои и их ответственность



| Слой | Ответственность | Не должен делать |

|------|-----------------|------------------|

| Controller | принимает запрос | не содержит SQL |

| Service | бизнес-логика | не рисует интерфейс |

| Repository | работа с БД | не принимает бизнес-решений |

| Database | хранение данных | не содержит UI |

&#x20;  4. Структура каталогов src/



src/

├── presentation/ — контроллеры



├── service/ — бизнес-логика



├── repository/ — работа с БД



├── models/ — модели данных



└── main.py — точка входа



\---



&#x20;  5. Ключевые классы



| Класс | Назначение | Вход | Выход |

|-------|-----------|------|-------|

| UserController | приём запросов | HTTP | вызов UserService |

| TicketService | логика заявок | данные | результат |

| TicketRepository | работа с БД | объект | сохранение |

| Ticket | модель заявки | — | — |

| Category | модель категории | — | — |



\---



&#x20;  6. Почему выбрана эта архитектура



За:

\- простота;

\- тестируемость;

\- понятное разделение.



Против:

\- много файлов для простой задачи.



Вывод: подходит для учебного проекта.
